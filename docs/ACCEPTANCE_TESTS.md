# End-to-end acceptance scenarios

Original Phase 0 scenario specifications. Execution evidence is in [Phase 5 deployment](PHASE_5_DEPLOYMENT.md) and [Phase 6 QA](PHASE_6_QA.md); do not interpret the historical planning text as current test results. Requirement IDs refer to [REQUIREMENTS.md](REQUIREMENTS.md). P = project rule/design invariant beyond explicit PDF wording. Execute against real FastAPI + isolated SQLite, not mocked messaging APIs. Alice, Bob and Carol use separate browser contexts/cookie stores; extra tabs test one account's multiple connections. Stabilize clock/fixtures for screenshots.

## Test evidence and release gates

- Use pytest with independent connections for DB/auth/security/race assertions, including malformed WS payloads and rate/size limits. Use Playwright isolated contexts for actual two-/three-user flows. Negative authorization requests may use an authenticated API client within the E2E test.
- On timing tests, wait for observable events with bounded timeouts, not arbitrary sleeps. Delays/failure injection belong to isolated tests, never publicly exposed production endpoints.
- For each run record command, environment, fixture revision, actual pass/fail, logs with credentials redacted, and screenshots for visual tests. Verify both UI and durable DB invariants where needed; HTTP 200 alone is insufficient.
- Planned commands once configured: frontend `npm run lint`, `npm run typecheck`, `npm run build`; backend `python -m pytest`; browser `npx playwright test`. Phase 1 must define the scripts explicitly. These commands have **not** been run in Phase 0.
- Core gate requires E01-E12 applicable checks passing, no outstanding unauthorized access/data loss, approved visual comparisons, and known deployment constraints documented. Bonuses cannot displace this gate.
